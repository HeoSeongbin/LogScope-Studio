# 운영 상황을 모사한 가상 테스트 로그

실제 운영 로그가 아닙니다. 쇼핑 서비스의 2026-11-16 14:00~15:30(+09:00) 트래픽을 가정해 생성한 합성 데이터입니다. 실제 고객/계정/결제정보/토큰을 사용하지 않았으며 IP도 문서 예시 대역입니다. 이 폴더의 .log/.jsonl 네 파일만 사이트에 업로드하세요. JSON 요약/검증 파일은 로그 입력이 아닙니다.

## 운영 시나리오

- 총 1,415개 HTTP 요청, 불규칙한 도착 간격과 서로 겹치는 서비스 처리
- 상품 조회·주문 생성·장바구니 변경·결제 승인·상태 점검
- 정상 1,189건, 정상 완료하되 지연된 요청 53건
- DB 연결/트랜잭션 실패 102건, 결제 제공자 타임아웃/재시도 실패 8건
- 입력 검증 거절 34건(400), 인증 거절 18건(401), 상품 없음 11건(404)
- 14:20~14:25에 트래픽 증가와 DB 오류 집중, 14:55~14:59에 결제 타임아웃 집중. 구간 밖에도 소수의 오류가 존재
- Spring SQL 예외의 원인 체인/공통 생략 프레임, .NET 내부 예외와 두 번의 결제 시도, 주문 실패 후 승인 취소 요청
- JSON의 HTTP 상태/소요시간/라우팅·서비스·호스트, 정상 시각 없는 진단 10개
- IIS 200/201/400/401/404/500/503/504, 응답 시간과 도중 #Fields 컬럼 순서 변경

이 수치는 생성 시나리오의 정답이며 사이트가 장애 원인을 자동으로 확정한다는 뜻이 아닙니다. 같은 HTTP 요청을 네 파일에서 여러 차례 관측하므로 11,108개 이벤트를 실제 요청 수로 읽지 마세요.

## 추천 테스트 순서

1. 네 로그를 함께 업로드하고 자동 감지로 분석합니다. 전체 이벤트 11,108개와 파싱 실패 2개를 확인합니다.
2. ERROR/WARN 레벨 필터, `데이터베이스 처리 실패`, `Payment authorization failed`, `transaction=ROLLED_BACK` 등을 검색합니다.
3. 예외 분석에서 반복 SQL 오류·원인 체인과 .NET 내부 예외를 살펴보고 원본 줄을 엽니다. 서비스/Logger/예외 구조가 다르면 별도 그룹이 되는 것이 정상입니다.
4. 요청 추적에서 `req-test-0034`(DB 실패), `req-test-0943`(결제 타임아웃), `req-test-0020`(지연), `req-test-0001`(정상)을 정확히 검색합니다. 이들 요청은 세 개 이상 파일에서 확인했습니다.
5. 파일 설정에서 Spring 서비스명을 `commerce-api`, .NET 서비스명을 `payment-api`로 지정하면 미기록 서비스의 사용자 라벨을 볼 수 있습니다. 실제 필드에서 읽은 서비스명과 구분됩니다.
6. Dashboard/Timeline에서 1분 또는 5분 버킷을 선택해 14:20대 오류 집중과 회복 이후 구간을 비교합니다. 화면의 버킷 시각은 UTC이므로 각각 **05:20대/05:55대 UTC**입니다.
7. CSV/JSON/HTML로 범위를 내보내고 파일 제거·재분석·세션 초기화를 확인합니다.

## 의도한 진단 / 시간 정밀도

JSON 마지막 행과 IIS 마지막 행은 로그 기록 중 잘린 상황을 가정했습니다. 각각 파싱 실패 1건과 원문이 남아야 합니다. JSON은 정상 진단 10개와 잘린 행을 합쳐 시각 미확인 11개, IIS는 잘린 행의 시각 미확인 1개가 있습니다. 이 두 실패를 프로그램 오류로 오해하지 마세요.

Spring/.NET/JSON은 +09:00 명시 시각이고 IIS는 규약상 UTC입니다. 별도 시간대 가정은 필요 없습니다. IIS는 초 단위, 나머지는 밀리초 단위라 같은 요청의 표시 순서가 세밀하게 일치하지 않을 수 있습니다. 요청의 최초~최종 관측 간격을 실제 처리시간이나 인과관계로 단정하지 마세요.

IIS의 HTTP 오류는 애플리케이션 ERROR 레벨/Exception으로 변환하지 않습니다. IIS 이벤트의 UNKNOWN 레벨은 정상입니다. HTTP 5xx는 110건, HTTP 4xx는 63건입니다.

scenario-summary.json은 생성 시나리오, verified-results.json은 현재 파서로 실제 읽은 파일별 건수입니다. 앱 원본/분석 코드·배포는 변경하지 않았습니다.
